# 0010. 엔티티 ID는 NanoID 12자

- 상태: 확정 (적용은 14-38)
- 날짜: 2026-11-26
- 이슈: 14-38

## 맥락

- 펀딩은 링크로 공유한다. 단체 대화방에 붙여 넣으므로 링크가 짧아야 한다.
- 상세 기획("펀딩 공유·참여코드")상 내 위시 펀딩은 링크를 받은 사람이 로그인만 하면 열람할 수 있고, 화면에 개설자의 받을 계좌가 보인다. 로그인은 소셜 로그인이라 누구나 통과한다.
- 그래서 ID를 대입해 다른 사람의 펀딩과 계좌를 훑지 못하게 해야 한다.

## 결정

- 모든 엔티티의 PK는 NanoID 12자로 한다. 알파벳은 영문 대소문자와 숫자 62자다(약 71비트). 컬럼 타입은 `varchar(12)`다.
- JDK `SecureRandom`으로 만든다(`nextInt(62)`로 치우침 없이). Hibernate `BeforeExecutionGenerator`를 구현한 생성기(`NanoId`)를 `@IdGeneratorType` 애너테이션(`@NanoIdGenerated`)으로 붙인다. 라이브러리는 쓰지 않는다.
- 모든 엔티티는 `BaseEntity`를 상속하고, PK는 `BaseEntity`에만 있다. ID에는 setter가 없어 직접 넣을 수 없다.
- 강제 수단:
  - ArchUnit: `BaseEntity`를 상속하지 않은 엔티티, `BaseEntity` 밖의 `@Id`·`@EmbeddedId`·`@GeneratedValue`
  - 스키마 검사: `id VARCHAR(12) PRIMARY KEY`가 없는 테이블
- 생성자나 필드 초기화로 ID를 직접 넣지 않는다. 넣으면 Spring Data `save()`가 새 엔티티를 merge로 처리해 SELECT가 한 번 더 나간다.
- URL과 API에는 이 ID를 그대로 쓴다. 공유 링크용 토큰을 따로 두지 않는다.
- 시드 SQL에는 ID를 직접 적는다. DB DEFAULT는 없다.

## 검토한 대안

| 대안 | 탈락 이유 |
|---|---|
| BIGINT IDENTITY/SEQUENCE | 순서대로 대입하면 다른 사람의 펀딩(계좌 포함)을 열람할 수 있다 |
| UUID v7 | 36자라 공유 링크가 길다 |
| NanoID 21자 | 약 125비트로 여유가 크지만, 12자로도 충돌 확률과 추측 난이도가 충분해 짧은 쪽을 택했다 |
| jnanoid 라이브러리 | 대신해 주는 것은 문자를 뽑는 반복문 몇 줄뿐이고, Hibernate 생성기는 어차피 직접 만들어야 한다. 마지막 릴리스가 2018-11이다 |
| UUID v7 PK에 URL에서만 base62 인코딩(22자) | DB 값과 URL·로그 값이 달라 조회할 때마다 변환해야 한다 |
| NanoID 기본 알파벳(`_`, `-` 포함) | `-`에서 더블클릭 선택이 끊긴다 |

## 트레이드오프

- **얻는 것:**
  - 공유 링크의 ID가 12자다.
  - 전부 무작위라 생성 시각이 드러나지 않는다. 무작위 부분이 약 71비트로 UUID v7(62비트)보다 많다.
- **잃는 것:**
  - PostgreSQL에 생성 함수가 없어 DEFAULT를 걸 수 없다.
  - PK와 FK가 문자열이다. 시간순이 아니므로 정렬은 `created_at`으로 하고, 인덱스 삽입 위치가 흩어진다. 이 규모에서는 무시한다.
  - 충돌 확률이 0은 아니다. 100만 건에서 약 10^-10이다. 중복은 PK 제약이 막고, 그 요청은 실패한다. 재시도는 넣지 않는다.
  - 생성기 코드를 직접 관리한다.
  - 링크가 곧 ID라서 유출된 링크 하나만 따로 막을 수 없다.

## 후속 확인

- 링크 재발급이나 폐기가 기획에 들어오면 공유 토큰 컬럼을 따로 두는 새 ADR을 쓴다.
