# 0016. 브랜치·커밋·PR 이름에 이슈 키를 넣고, 커밋은 CI가 검사한다

- 상태: 확정
- 날짜: 2026-11-26
- 이슈: 14-45

## 맥락

11/25 회의에서 "이슈 기준 피쳐 브랜치 → `develop` PR"로 정했다. 합칠 때 스쿼시하지 않아 피쳐 브랜치의 커밋이 그대로 `develop` 이력이 된다(합치는 방식은 [0020](0020-promotion-fast-forward-bot.md)). PR 제목은 git 이력에 남지 않는다.

## 결정

| 항목 | 규칙 | 예 |
|---|---|---|
| 브랜치 | `feature/{이슈 키}` | `feature/14-38` |
| 커밋 | `{타입}({이슈 키}): 요약`. 타입은 `feat`, `fix`, `refactor`, `test`, `docs`, `chore` | `feat(14-38): 엔티티 공통 규칙 추가` |
| PR 제목 | `[{이슈 키}] 요약` | `[14-38] 엔티티 공통 규칙` |
| 배포 | `develop` → `production` PR, 그다음 `production` → `main` PR. `production`에 태그 `v{YYYYMMDD}-{짧은 해시}` | `v20261126-4477a70` |

- CI(`naming` 잡)가 `develop`으로 오는 PR의 브랜치 이름과 모든 커밋 메시지를 검사한다. 이후 PR 제목 검사([0021](0021-promotion-pr-title-template-no-coderabbit.md))와 핫픽스 PR 검사([0022](0022-hotfix-to-production.md))가 더해졌다.
- 브랜치 이름은 PR 작성자가 정하는 값이라, 스크립트에 직접 넣지 않고 환경변수로 넘긴다(명령 주입 방지).

## 검토한 대안

| 대안 | 탈락 이유 |
|---|---|
| 커밋에 키 없음(`feat: 요약`) | 합친 뒤에는 이력만 보고 어느 이슈의 작업인지 알 수 없다 |
| `[14-38] feat: 요약` | 눈에 잘 띄지만 Conventional Commits 형식에서 벗어난다 |
| 스쿼시 머지 | 회의에서 커밋을 하나로 합치지 않기로 정했다 |

## 트레이드오프

- **얻는 것:**
  - `develop` 이력의 모든 커밋에서 이슈를 바로 찾는다.
  - 형식 위반은 사람이 아니라 CI가 잡는다.
- **잃는 것:**
  - 작은 수정도 먼저 이슈를 만들어야 한다.
  - 커밋 메시지를 잘못 쓰면 PR을 올리기 전에 고쳐야 한다(amend, rebase).
  - 승격 PR(`develop` → `production` 등)은 검사하지 않는다. 그 커밋들은 `develop`에 들어올 때 이미 검사를 거쳤다.
